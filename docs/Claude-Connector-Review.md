# Claude connector integration review

**Verdict: no confirmed material source defect found in the reviewed Claude-native read-only connector.** The current working tree satisfies the requested read-only boundary, token/account isolation, persisted OAuth grant flow, and consent-return safeguards. This was a source trace plus targeted TypeScript diagnostic, not a deployment or live-Claude verification.

## Confirmed findings

- **No anonymous MCP discovery or data access:** `server/steadier/mcp.ts:374-410` rejects URL queries and disallowed browser origins, validates a Bearer reader key before entering the SDK handler, and attaches only a validated owner-scoped auth context. Missing/expired/revoked keys fail closed with a resource-metadata challenge (`mcp.ts:86-94`, `service.ts:213-238`). Browser session cookies are not accepted as MCP credentials.
- **Per-request owner isolation and read-only tools:** the SDK factory derives the owner only from that validated request context and creates a scoped server (`mcp.ts:341-350`); each tool reads that owner’s workspace (`mcp.ts:197-333`). The owner-isolation/read-only behavior is exercised with two users and a no-write repository double in `server/steadier/mcp.test.ts:284-491`.
- **OAuth binding and replay controls are present:** authorization persists client, exact redirect URI, state, S256 challenge, scope, resource, and short expiry (`compassOAuth.ts:600-640`); consent requires an authenticated matching owner and a guarded JSON POST (`compassOAuth.ts:643-722`); token exchange rechecks client/redirect/resource/PKCE then atomically consumes the code before minting a 90-day hashed reader key (`compassOAuth.ts:726-777`). The production repository persists this state, claims owner-bound requests, inserts the approval/code transactionally, and conditionally redeems codes (`oauthRepository.ts:271-394`).
- **Cross-pod durability:** OAuth clients, requests, and hashed authorization codes are additive MySQL tables (`drizzle/schema.ts:81-140`, `drizzle/0002_wise_bastion.sql:1-46`); reader-key lookup and revocation remain database-backed (`server/steadier/repository.ts:201-274`). No grant, code, client registration, or reader credential is stored only in process memory. The in-process DCR rate limiter is an abuse brake only, not authorization state.
- **Credential handling:** reader tokens and authorization codes are minted randomly but only hashes are persisted (`service.ts:174-210`, `compassOAuth.ts:686-702`); no refresh token is issued (`compassOAuth.ts:755-773`). Tool responses carry data but do not echo reader credentials. OAuth/MCP error paths suppress sensitive request-context logging (`mcp.ts:354-356`, `compassOAuth.ts:92-105`).
- **Discovery/DCR compatibility:** protected-resource and authorization-server metadata advertise the fixed canonical HTTPS resource/issuer, S256 PKCE, public dynamic registration, and `client_id_metadata_document_supported: false` (`compassOAuth.ts:535-568`). Redirect registration and authorization use exact validated registered strings (`compassOAuth.ts:193-228`, `600-621`).
- **Consent and login return:** the client obtains the session first, then sends the account-binding header through the existing private API helpers (`ClaudeConsent.tsx:36-67`; `client/src/lib/cloudApi.ts:21-36,60-84`). Approval verifies the returned redirect against the consent view’s registered origin before navigation (`ClaudeConsent.tsx:69-100`). The core callback preserves its nonce check and returns only to the fixed in-app consent route after validating the short-lived cookie ticket (`server/_core/oauth.ts:29-45,74-87`), rather than accepting an external return URL.
- **Existing behavior is preserved:** the consent page is rendered before normal home content, and focus timer writes are disabled while the consent ticket is active (`client/src/pages/Home.tsx:65-69,130-158,336-344`). The connector guidance explicitly retains opt-in voice/refocus behavior and rejects monitoring claims (`ClaudeSetup.tsx:138-143`; `shared/compassConnection.ts:24`).
- **Current source integration:** `server/_core/index.ts:26-30` now mounts both OAuth and MCP routes before the API fallback. This addresses the mount that was known to be absent at review start; it was not counted as a defect.

## Evidence and limits

- `pnpm check` completed successfully during this review. I did not request or run an extra full suite.
- The dedicated synthetic tests cover MCP SDK discovery/calls, no-write behavior, owner isolation, expired/revoked keys, DCR, PKCE S256, redirect/client/resource mismatch, owner binding, denial, and atomic code replay (`server/steadier/mcp.test.ts`, `server/steadier/compassOAuth.test.ts`).
- The currently published site is explicitly outside this source review and is known to predate the connector. **Publication of this exact version, migration application, and a real Claude-account configuration/authorization run remain unverified release steps**, not source-level security defects.

## Integrated release checks after the source review

The parent applied the inspected additive migration and mounted both registrars before the API fallback. Full source checks passed: 64 tests across 12 files, TypeScript and production build. Actual registered OAuth metadata was HTTP 200 and anonymous MCP was HTTP 401 with the standard resource-metadata challenge.

The full synthetic HTTP/browser flow found a runtime SDK behavior not visible in the initial source trace: responseMode=json applies only to the modern protocol; legacy Streamable HTTP responses use SSE and set their own no-cache header. The parent fixed this by enforcing private,no-store,no-transform on the final Web response before Node writes it. Official SDK-client regression assertions now cover private/no-store headers on all successful modern and legacy MCP replies. The smoke script correctly handles both JSON and legacy SSE rather than claiming every era uses JSON.

The parent also allowed authenticated calls carrying Claude's exact trusted origin while continuing to reject hostile origins, and required OAuth approval in a standalone browser window to resist framed/clickjacked approval without denying normal app Preview embedding. A phone-size browser check verified the framed approval control is disabled, and standalone approval still works.

A synthetic-only end-to-end check exercised dynamic registration, actual durable owner binding, anonymous/other-owner concealment, explicit browser permission and optional read-aloud/stop, original OAuth client state, PKCE exchange, code replay rejection, MCP discovery/context retrieval with private headers, unchanged saved workspace, exactly one issued reader, normal key revocation and immediate subsequent read denial. Browser callbacks were intercepted locally rather than submitting synthetic codes to Claude. No real user's tasks, authorisations or microphone were used. Real Claude account setup remains a user step; these checks establish app-side interoperability and privacy, not that user's configured connection.
